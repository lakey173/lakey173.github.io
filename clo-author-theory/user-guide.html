User Guide

Complete Workflow for Applied Economic Theory Research

The Theory Research Pipeline

/discover interview  →  Research Spec + Domain Profile
        ↓
/discover lit        →  Literature Synthesis (Librarian + librarian-critic)
/discover model      →  Modeling Landscape (Literature-explorer + literature-explorer-critic)
        ↓
⚠ ONLINE APPENDIX GATE — user uploads published-paper appendices
        ↓
/model               →  Model Memo (Model-Designer + model-critic)
        ↓
/sanity              →  Model Sanity Check ← REQUIRED GATE (must PASS)
        ↓
/solve               →  Proofs + Computation (Derivation-engineer ∥ Theory-coder)
        ↓
/write               →  Paper Sections (Writer + writer-critic)
        ↓
/review              →  Quality Score + Peer Review (domain-referee + theory-referee)
        ↓
/submit              →  Final Gate (score ≥ 95, all components ≥ 80)

Enter at any stage. Use /new-project for the full pipeline.

Phase 1: Discovery

Three modes:

/discover interview [topic]

Structured interview to formalize your research idea. Claude asks about your modeling tradition, key assumptions, equilibrium concept, and expected results. Produces a research specification and fills in the domain profile.

/discover lit [topic]

Comprehensive literature review. Dispatches the Librarian + librarian-critic pair. Searches top-5 generals (AER, QJE, JPE, Econometrica, REStud), NBER working papers, field journals, SSRN/RePEc. Produces annotated bibliography with proximity scores, BibTeX entries, and a frontier map.

/discover model [topic]

Modeling landscape exploration. Dispatches the Literature-Explorer + literature-explorer-critic pair. Searches for papers using similar model structures. Pays special attention to online appendices where proof machinery lives. Produces proof technique catalog and benchmark model identification.

⚠ Online Appendix Gate. After /discover model scores ≥ 80, the pipeline pauses. The Literature-explorer lists proximity-1 and proximity-2 papers and asks you to download their online appendices into master_supporting_docs/. This ensures proof techniques from benchmark papers are available before model design — not discovered mid-derivation. NBER working papers bundle appendices in the main PDF; no separate download needed.

Phase 2: Model Design

/model [research question] — Dispatches the Model-Designer + model-critic pair.

The Model-Designer proposes a complete model setup:

  • Players and their roles
  • Information structure (who knows what, when)
  • Timing (sequence of moves)
  • Strategy spaces
  • Payoff functions
  • Equilibrium concept with justification
  • All assumptions (numbered: A1, A2, ...)
  • Benchmark model and parameter mapping
  • Tractability assessment (closed-form? implicit? numerical?)
  • Expected results and objects of interest

The model-critic evaluates through 5 sequential phases (with early stopping):

  1. Can the model answer the research question?
  2. Is the model setup sound?
  3. Is the model tractable?
  4. Does it produce interesting results?
  5. Literature fit and generality?

Must score ≥ 80 to proceed.

Phase 3: Sanity Check

/sanity — Required gate between model design and derivations.

Checks 7 critical items:

  1. Interior solution exists (or corner is interesting and intended)
  2. Equilibrium is not degenerate
  3. Parameters are not knife-edge
  4. Comparative statics are well-defined
  5. Objective is concave where assumed
  6. Equilibrium existence is plausible
  7. Solution is not trivial

Plus 1 advisory item:

  1. Testable predictions exist

Hard Gate. If any critical item fails, you return to /model. Derivations do NOT begin until sanity PASS. This saves weeks of wasted work on models that don't have well-defined equilibria.

Phase 4: Execution

/solve — Dispatches three agents in parallel:

Derivation-Engineer

Produces formal proofs in LaTeX:

  • First-order conditions and second-order checks
  • Equilibrium existence and uniqueness
  • Equilibrium characterization
  • Comparative statics (all parameters of interest)
  • Welfare analysis (if applicable)
  • All proofs use \begin{proof}[Proof of \cref{prop:X}] format

Theory-Coder

Produces computational verification:

  • Symbolic verification (SymPy/Maple): verify FOCs, closed-form solutions, comparative statics signs
  • Numerical illustrations: equilibrium across parameter grids
  • Publication-quality figures (matplotlib): comparative statics plots, best-response diagrams
  • Verification log: analytical vs. numerical results for every proposition

Theory-Coder-Critic

Reviews both:

  • Cross-checks proofs against code
  • Verifies proof-code consistency
  • Flags any proposition where analytical and numerical results disagree

Phase 5: Writing

/write [section] — Dispatches the Writer + writer-critic pair.

Available sections: intro, model, equilibrium, results, conclusion, appendix, full

Theory paper conventions enforced:

  • Contribution statement in first 2 pages of introduction
  • All assumptions numbered (A1, A2, ...) and formally stated before first use
  • Every proposition cites its appendix proof
  • Proof sketches in main text must not be stronger than full proofs
  • \cref{} for all cross-references
  • Anti-hedging pass (removes "interestingly", "arguably", "it is worth noting")
  • Humanizer pass (strips 24 AI writing patterns)

/write humanize [file] — Standalone humanizer pass on existing text.

Phase 6: Review

/review — Routes to appropriate critics based on flags.

Flag What It Does Agents
(no flag, .tex file)Comprehensive reviewwriter-critic + theory-coder-critic + verifier
--peer [journal]Full peer revieweditor → domain-referee + theory-referee → editorial decision
--stress [journal]Hostile stress testBoth referees skeptic + 2 critical pet peeves each
--proofsProof review onlytheory-coder-critic (4 categories)
--codeComputation review onlytheory-coder-critic (code categories)
--proofreadManuscript polishwriter-critic (6 categories)
--allPaper excellenceAll critics in parallel

Peer review simulates the editorial process:

  1. Editor desk-reviews (novelty check, desk reject or send to referees)
  2. Two independent referees (domain-referee + theory-referee) produce blind reports
  3. Editor synthesizes decision: Accept / Minor / Major / Reject

Phase 7: Revision

/revise [referee-report] — Routes referee comments by classification:

  • NEW ANALYSIS → Theory-coder (new computation needed)
  • CLARIFICATION → Writer (text revision sufficient)
  • DISAGREE → Flagged for you (never autonomously pushes back on referees)
  • MINOR → Writer (typos, formatting)

Produces point-by-point response letter mapping each comment to specific changes.

Phase 9: Submission

/submit modes:

  • target — Rank 3 target journals with rationale
  • package — Build replication package
  • audit — Verify replication package
  • final [journal] — Final gate: score ≥ 95, all components ≥ 80. Generates cover letter and submission checklist.

Exploration Workflow

For experimental model sketches and proof-of-concept work:

  • Work in explorations/ folder
  • 60/100 quality threshold (vs. 80/100 for production)
  • No plan needed — just create, verify, decide (keep/graduate/archive)
  • Graduate to production when quality ≥ 80 and results verified

When Claude Asks You

Claude pauses and asks for your decision on:

  • Model design forks: "Option A (screening) vs. Option B (signaling). Which?"
  • Equilibrium concept: "PBE vs. NE for this information structure?"
  • Sanity failure: "Model fails interior solution check — revise model or proceed with corner?"
  • Disagreement with referee: "DISAGREE classification — please review"
  • After 3 strikes: "Derivation-engineer and theory-coder-critic can't agree — your call"

Claude executes without asking on:

  • Obvious algebraic manipulations in proofs
  • Verification (compilation, consistency checks)
  • Documentation (logs, commits)
  • Figure generation per established standards

Troubleshooting

LaTeX doesn't compile — Run the 3-pass sequence: xelatex → biber → xelatex → xelatex. Make sure cleveref loads after hyperref.

SymPy verification fails — Check that your model's functional forms match between the model memo and the verification script. Common issue: different variable names.

Sanity check keeps failing — The model may have a fundamental issue. Don't try to force it through — revisit the model setup with /model.

Agent loops (3 strikes) — The system escalates automatically. If you see repeated failures, it usually means the model needs revision, not the proof technique.

Context getting long — The system auto-compresses. Important state is saved to disk (plans, session logs, MEMORY.md). After compression, Claude resumes by reading the most recent plan.
